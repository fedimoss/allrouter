# 注册人机验证

## 流程

1. 用户填写邮箱，点击发送验证码。
2. 服务端生成随机图案顺序点选题：从 16 个随机排列、旋转和着色的图案中，按示例顺序点选 5 个。
3. 验证通过后，浏览器自动请求发送邮件验证码。
4. 同一 IP 或同一服务商下的同一邮箱，发送间隔至少 60 秒；拒绝的请求不会延长倒计时。
5. 用户输入邮件验证码，继续原有用户名、密码、邀请码、时区、注册 IP 和默认令牌流程。

重新发送需要重新完成人机验证。关闭邮件验证设置时，注册提交本身仍需要人机验证。已有第三方 OAuth、管理员创建用户和邮件绑定流程保持各自原有逻辑。

## 接口

新增接口都使用 POST JSON，响应禁止缓存：

- `/api/user/register/captcha`：`{ "email": "user@example.com" }`，返回题目 ID、提示 PNG、图案 PNG、尺寸和有效期，不返回答案或生成种子。
- `/api/user/register/captcha/verify`：`{ "email": "user@example.com", "challenge_id": "...", "clicks": [{ "x": 100, "y": 80, "time_ms": 1200 }] }`。坐标使用响应中的逻辑尺寸，每次必须提交完整的 5 个点选。
- `/api/user/register/verification`：`{ "email": "user@example.com", "captcha_token": "email_token" }`，验证一次性发信授权后发送原邮件验证码。
- `/api/user/register`：在原注册 JSON 中增加 `captcha_token`，使用上一步验证返回的 `registration_token`。

原 GET `/api/verification` 仅供已登录用户绑定邮箱使用，要求正常用户认证，不能作为匿名注册发信的旁路。

发信成功返回 `retry_after: 60`。发送过于频繁时返回 HTTP 429、`Retry-After` 响应头及 `retry_after` 秒数，前端按服务端剩余时间倒计时。邮件模板生成、验证码存储或 SMTP 发信失败时，会释放本次预占的发送额度，不占用 60 秒冷却；注册用户重新完成人机验证后可立即重试。回滚仅释放本次请求的额度，避免延迟结束的旧请求影响新的发送。

## 安全与存储

- 图案由服务端绘制为 PNG，没有文字识别题，也不在前端 SVG、DOM 或响应元数据中暴露答案。
- 每题有效期 2 分钟，仅允许提交一次答案；同一 IP 每分钟最多获取 5 题。
- 验证成功产生两个独立的 256 位随机授权：发信授权有效期 2 分钟，注册授权有效期 10 分钟。两者用途隔离，各自只能使用一次。
- 题目与授权绑定浏览器会话、客户端 IP、服务商和规范化后的邮箱；更换邮箱、浏览器或 IP 后不能复用。
- 错误的注册表单或邮件验证码不会消耗注册授权；插入用户前原子消费授权，阻止并发重放。
- 题目、授权和 60 秒限流均支持共享 Redis。启用 Redis 后，Redis 异常会拒绝请求，不退化到单机内存绕过跨节点保护。
- 未启用 Redis 时使用带互斥锁、过期清理和容量上限的内存存储。多实例部署应启用共享 Redis、配置相同的 `SESSION_SECRET`，并保持服务器时间同步。
- 会话 Cookie 只记录随机的浏览器标识，不保存答案或已通过标志。
- 不新增数据库表或迁移，SQLite、MySQL 和 PostgreSQL 的原注册持久化逻辑不变。

图案点选能避免单纯文字 OCR 直接解题，但不能保证阻止视觉模型、图像匹配或真人打码。高风险部署建议同时启用项目已有的 Turnstile 与网关层风险控制。

## 部署和验证

需要一同部署新前端与后端。邮件设置、邮件验证码有效期和注册开关仍使用现有配置。

```powershell
cd web
bun run build
cd ..
go build .
go test ./pkg/registrationcaptcha ./middleware ./common ./router
```

新增测试覆盖题目答案隔离、过期、会话/邮箱/IP/服务商绑定、用途隔离、并发消费、并发限流、Redis 故障及邮件发送后继续注册。控制器端到端测试使用独立内存 SQLite、Redis 测试服务和本地 SMTP，不会向真实邮箱发送邮件。
